## 问题与处理办法

### R01：默认 LLM 的创建位置不合理

**你的发现：** `build_agent()` 没传入 LLM 时，最终仍由 Agent 内部的 `llm or LLMClient()` 创建默认客户端，解耦没有做彻底。

**问题所在：** 已经支持注入自定义 LLM，但主循环仍依赖具体客户端及其创建方式，同时承担装配职责。

**确定的改进方向：** 默认客户端由组合根创建，通过参数传给 Agent；主循环只使用客户端接口。默认值判断使用 `if llm is None`。

**状态：已完成。** 2026-09-26 随会话管理拆分，将默认客户端创建移到 `bootstrap.py`，使用 `if llm is None` 判断，并注入会话入口与执行器。

### R02：系统提示词存在两个输入入口

**你的发现：** 主循环已经把系统提示词放进 `messages`，`LLMClient.chat()` 又单独接受 `system_prompt`，职责重叠。

**解决办法：** 系统提示词统一由调用方组装成 `role="system"` 消息；模型客户端负责发送调用方提供的消息。

**状态：已修复。** 删除了 `chat(system_prompt=...)` 参数及相应的系统消息覆盖、过滤逻辑。

### R03：工具调用附带文字不应直接作为中间话术

**你的发现：** 实际测试中，工具调用响应不一定产生附带文字；即使产生，也不一定适合展示给用户。当前提示词本身也限制这类输出。

**解决办法：** 在 `response.tool_calls` 分支只记录工具调用请求，丢弃该响应附带的 `content`。该文字既不进入最终回复，也不写入 assistant 工具调用消息。

**状态：已调整。** 普通回答分支仍正常使用 `response.content`；这次调整针对工具调用附带文字。

### R04：`visible` 命名不准确

**你的发现：** 这个列表实际承担的是收集最终回答的职责，`visible` 太宽泛，容易被理解为所有用户可见内容。

**解决办法：** 重命名为 `final_replies`。

**状态：已完成。** 当前由 `AgentState.final_replies` 保存本次运行的最终回复，并复制到 `TurnResult.replies` 返回。

### R05：工具参数解析失败不应伪装成空参数

**你的发现：** 参数处理应该明确完成 JSON 到字典的转换；模型产出错误时，不应把错误隐藏成 `{}` 后继续执行工具。

**需要区分：** `json.loads(args_str) if args_str else {}` 中，空输入会直接变成 `{}`；非空但残缺的 JSON 会在 `json.loads()` 处抛异常。两者都不能与显式传入合法的 `"{}"` 混为一谈。

**解决办法：** 直接解析 JSON，并确认结果是对象。空输入、非法 JSON、非对象 JSON 返回明确参数错误，跳过工具执行，再通过对应的 tool 消息要求模型修正。

**状态：已修复。** 显式的 `"{}"` 仍能通过解析，是否满足某个工具的要求由后续参数校验决定。解析失败事件的 `args` 记为 `None`；同批其他合法调用仍可执行。

### R06：工具结果压缩不应放在主循环统一处理

**你的发现：** 希望从工具设计本身减少冗余，而不是让 Agent 在得到结果后再统一压缩。

**问题所在：** 通用压缩层需要知道各个工具的字段规则，增加核心与领域的耦合；字段过滤或截断也可能让后续推理缺少证据。

**解决办法：** 移除 `compress_tool_result`、压缩模块及 `tool_field_map` 配置链路，由工具负责返回合适的数据。

**状态：压缩功能已移除。** 工具如何进一步精简输出仍属于后续工具设计工作。

### R07：工具返回值的序列化责任不明确

**你的发现：** 当前工具主要服务 Agent，可以统一让工具直接返回合法 JSON 字符串，减少调用层的重复处理。

**解决办法：** 五个本地电商函数统一返回 JSON 字符串，`_safe_call_tool()` 正常路径只透传结果，调用异常仍由它生成错误 JSON。旧分派器和 Provider 包装已在 R17 中删除，函数的返回约定保留。

**状态：已完成。** 商品搜索、商品详情、库存、FAQ 和知识搜索都已调整；空结果返回 JSON 字符串 `"[]"`。`-> str` 表达类型约定，JSON 合法性由工具实现保证，并没有给主循环新增重复校验。

### R08：本地执行故障不应统一交给 LLM 反复尝试

**你的发现：** 参数错误应让产出参数的 LLM 修正；但参数正确后，本地执行环节出错，需要本地承担相应的恢复责任。当前实现容易把两类问题都交回 ReAct 循环兜底。

**当前行为：** `_safe_call_tool()` 捕获异常并返回错误 JSON，循环继续，由模型决定下一步。它本身没有进行本地重试。

**已明确的方向：** 工具名或参数错误反馈给模型；对可安全重试的本地或依赖服务临时故障，考虑有限重试。永久错误、权限问题等不应盲目重试，重试耗尽也不能伪装成成功或空结果。

**状态：待设计，暂不实施。** 异常分类、重试所在层、次数与等待时间、幂等性、与已有回退逻辑的关系，以及耗尽后的处理方式，都需要继续梳理。此前讨论的“首次执行加两次重试、等待 0.5/1 秒”只是示例，尚未定案。

### R09：没有消费点的 `to_dict()`

**你的发现：** 会话历史类和旧记忆状态类都定义了 `to_dict()`，但当前项目没有实际调用方。

**解决办法：** 全项目检查消费点后，删除这两个无调用的方法。

**状态：已完成。** 后续移除恢复功能时，又删除了历史容器的 `from_dict()`；旧记忆状态类也已整体删除。

### R10：自检的触发条件与目标需要调整

**你的发现：** 不应该只有调用工具之后才自检；自检也应围绕任务完成情况发挥作用。

**确定的检查目标：** 用户要求是否完成、回答是否有证据、还有哪些信息无法确定。

**此前的阶段性调整：** 曾使用 `REFLECTION_ENABLED` 统一控制开关；模型生成回答草稿后可以自检，不再以使用工具为前提。循环上限后的收尾回答也会自检，并通过 `can_continue=False` 禁止要求继续补查。

**状态：2026-09-26 已删除当前模式。** 用户认为其应用过于机械，决定先移除。自检实现、领域提示词、开关、装配参数及主循环分支均已删除；普通最终回答和循环上限后的收尾回答直接记录并返回。R11 中讨论的替代方案尚未实现。

### R11：草稿可能影响自检器的独立判断

**你的发现：** 将 `draft` 暴露给自检器，可能让它顺着已有答案判断。你提出让它只接收 `user_query`、`tool_events`、`can_continue`。

**讨论中的方案：** 将自检提前为回答生成前的需求与证据检查，独立判断哪些要求已满足、缺少哪些信息，再决定补查或生成回答。

**尚未解决的取舍：** 不看草稿可以减少其影响，但无法核对最终回答是否误读证据。例如工具结果是“库存为零”，草稿却说“有货”，只检查证据是否齐全无法发现这个错误。只传当前问题也可能遗漏前几轮仍有效的约束。

**相关待定点：** 讨论中还指出，旧自检调用失败或判定无法解析时，默认返回 `accept`；未来若引入新的检查机制，需要区分“未完成检查”和“检查通过”。

**状态：旧实现已于 2026-09-26 删除，未实施重设计。** 保留这些讨论供未来设计参考；尚未新增不看草稿的检查器，也未新增其他自检流程。

### R12：用户侧结果不应夹带工具轨迹

**你的发现：** `_make_result()` 返回的 `tool_calls` 对普通调用方未必必要，工具调用轨迹更适合单独放在调试或评测结构中。

**解决办法：** `TurnResult` 只包含 `replies` 和 `usage`；`RunTrace` 保存 `tool_events`，由 `AgentState.trace` 持有，通过 `agent.last_trace` 属性提供给调试和评测。

**状态：已完成。** 2026-09-26 将轨迹归入 `AgentState`。每次运行创建新的状态和轨迹，`agent.last_trace` 返回 `agent.state.trace`，二者访问同一个对象。评测继续从 `agent.last_trace.tool_events` 获取事件；保存旧状态的调用方仍可查看对应轮次的工具轨迹。

### R13：旧 State 与记忆落盘设计职责混杂

**你的发现：** 旧记忆及落盘设计不够合理；进一步讨论后，你决定移除当前 State 功能，换成常规 `AgentState`，同时删除落盘与恢复。

**讨论中定位的问题：** 旧 State 实际承担的是 LLM 用户事实摘要、轮次日志，而不是结构化运行状态；同步提炼会增加一次模型调用和回复等待。记忆提炼与保存放在同一个 `try` 中，提炼失败会连带跳过保存；直接覆盖写文件缺少原子替换，加载时也缺少结构校验。200 字摘要加最近窗口不能等同于完整会话归档。

**最终处理：** 删除旧记忆提炼、轮次记录组装、会话快照读写和恢复入口，以及对应的领域提示词、Web 用户画像和评测记忆断言。引入由程序维护的 `AgentState`。

**状态：已按决定替换。** 新状态记录 `user_input`、`messages`、`step`、`status`、`final_replies` 和 `trace`，每次 `run()` 重新创建。历史对话留在 `agent.history`，工具轨迹由 `agent.state.trace` 持有，也可通过 `agent.last_trace` 访问。上述旧持久化问题通过移除功能退出当前范围，并未另行实现一套持久化方案。

### R14：历史窗口外的信息缺失与内存持续增长

**你的发现：** 模型只能看到最近 10 条消息，更早的消息虽然仍在内存里，却无法参与本轮回答。

**原有行为：** `ConversationHistory.messages` 持续追加历史，`get_window(10)` 只返回末尾切片，不删除前面的记录。10 条按消息计数，用户一句和助手一句分别算一条。

**问题所在：** 移除旧记忆提炼后，没有摘要或检索补充窗口外的信息。早期预算、偏好、排除条件等约束可能从上下文中消失；同时内存中的完整历史仍不断增长。

**当前方案：** 未压缩原文超过 20 条时，按完整问答增量摘要，保留最多 10 条近期原文。系统提示词、旧对话摘要和全部未压缩原文共同组成上下文；摘要成功才释放原文，失败则保留原文继续回答。摘要调用计入本轮用量。

**状态：2026-09-27 已实现第一版。** 用户选择先补足窗口外信息。14 项离线测试验证摘要接入与失败保护、增量批次、会话隔离和长对话容量；真实模型对有效要求、改口与取消的摘要质量仍需实测。当前没有持久化，持续摘要失败时保留原文，token 预算尚未实现。详见 [CONVERSATION_MEMORY.md](CONVERSATION_MEMORY.md)。

### R15：明确什么时候不该使用 Agent，增加入口意图路由

**你的发现：** 应增加 intent router，把适合固定工作流的请求提前分流。用户只是简单问候或明确捣乱时，无需进入 ReAct 和自检，从而提高稳定性、降低成本。

**当前行为：** `ConversationRunner.run()` 统一接收请求，入口路由选择直接回复、固定商品查询或 ReAct。问候及明确单商品查询可由规则完成，无需调用模型；规则未覆盖时至多一次分类。

**设计方向：** 在 ReAct 之前识别意图。简单问候、明确越界或无有效业务诉求的捣乱请求采用固定回复或引导；步骤明确、参数可校验的业务需求走固定工作流；需要动态选工具、多步推理或根据结果调整计划的需求才进入 Agent。固定回复跳过 ReAct 与自检，固定业务流程保留各自必要的参数和结果校验。

**后续事项：** 用真实请求评测分类准确率、需求遗漏率与总成本；按结果决定是否替换分类模型、扩展规则或增加工作流。当前不使用模型自报置信度作为执行依据。

**状态：2026-10-10 已实现第一版。** 详见 [INTENT_ROUTING_DESIGN.md](INTENT_ROUTING_DESIGN.md)。库存、价格、通用参数查询复用 LocalProvider，并校验结果后用模板作答；复杂请求与分类失败回退 ReAct，工具执行失败不重复查询。历史、轨迹、分类用量和整轮耗时统一记录。离线测试验证机制，真实分类效果仍待评测。

### R16：会话管理与 ReAct 算法应独立

**你的发现：** 当前 `loop.py` 同时管理历史、上下文、状态生命周期、模型用量和 ReAct 循环；你要求先将会话管理与算法拆开。

**解决办法：** 新增 `ConversationRunner.run(user_input)` 负责历史、上下文组装、状态创建与完成/失败、最终回答记录、用量和 `TurnResult`。`ReActExecutor.execute(state)` 只更新执行消息、步数与工具事件，返回最终回答字符串。最终回答由会话入口统一记录一次。

**状态：已完成。** `build_agent()` 返回会话入口，外部 `.run(...)` 用法保留。原有窗口大小、工具错误反馈、循环上限和兜底行为保留；路由和固定工作流尚未实现。12 项离线测试与相关 Python 编译检查通过。

### R17：工具接入层拆除后重建

**你的决定：** 删除现有本地函数之外的工具实现层，保留通用 ReAct 工具调用流程，默认不接入工具。

**处理：** 删除工具清单、业务参数模型、schema 生成、查找表、`ToolDispatcher` 与 `providers/` 包装；保留五个本地业务函数及数据、检索依赖。`contract/tool.py` 只定义 `list_tools()` / `call()` 接口，核心和装配入口默认 `tools=None`，不再自动加载工具数据或创建检索服务。

**状态：已完成拆除，工具层待重建。** 会话、摘要、状态、工具往返协议和轨迹继续保留。默认应用能够对话，但无法查询本地业务数据；提示词已同步这个限制。

## 已澄清的疑问

- `_append_tool_calls()`、`_tool_message()` 和 `_build_event()` 有数据交集，但用途不同：前两者维护模型对话协议，后者组织工具事件，供调试和评测使用（旧自检曾消费这些事件）。尚未认定这些函数应因“重复记录”而删除。
- `TurnResult` 与 `AgentState` 是数据结构约定；类型注解和普通 dataclass 不自动强制检查字段值。调用方不执行运行时类型检查，本身不等于缺陷，目前没有决定增加强制校验。
- `AgentState.step` 表示 ReAct 循环步数，尚未细分“模型请求、执行工具、自检”等阶段；`completed` 表示正常返回，包括兜底回复，不代表任务必然成功。此前已澄清这些语义，尚未提出单独的修改要求。
