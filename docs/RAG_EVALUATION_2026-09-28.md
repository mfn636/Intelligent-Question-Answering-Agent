## 3. 如何测评

1. **固定数据。** 使用现有 `data/retrieval_golden.json` 的全部 270 条查询，不修改标签、不筛选有利样本。共覆盖 135 个目标文档，每个目标有两种问法；每条查询只标一个目标。

2. **审计索引。** 只读检查现有向量库：商品 80 个片段，知识库 536 个片段，共 616 个片段、298 个父文档。逐项比对当前分块代码生成的 ID、文本与业务元数据，未发现缺失、额外或变更片段，所有目标 ID 均可找到。商品和知识库各抽一个片段重新向量化，与旧向量余弦相似度约为 1；这只是抽样一致性检查。

3. **固定检索入口。** 商品查询进入 products，其余进入 knowledge；不附加类别过滤。集合选择依据已有标注预先确定，不将目标 ID 传给检索器。评测只衡量检索，不衡量 Agent 选工具或选集合的能力。

4. **固定算法参数。** 纯向量使用本地 Ollama 的 BGE-M3（1024 维），召回 20 条；纯向量路径保留原代码 0.3 阈值与兜底行为。混合路径在同一向量召回基础上加入 BM25 Top-20，RRF 的 k=60，融合后保留 20 条。复用项目的 `Retriever`、BM25 和 RRF 实现；本次向量返回的最低分超过 0.40，0.3 阈值没有删掉候选。

5. **固定评价单位。** 对实际返回的前 K 个片段，使用 payload.doc_id 映射到父文档；FAQ 和商品使用自身 ID。只做精确 ID 匹配，不使用字符串前缀匹配，不在截取 Top-K 前去重。同一文档多个片段不能累计成多个相关文档。

6. **计算配对指标。** 单条 Recall@K＝前 K 条中命中的已标注相关文档数÷该问题的已标注相关文档总数，再对查询取平均。本集合每题一个标签，因此这里 Recall@K 等同目标文档 Hit Rate@K。MRR@5 看第一个目标片段的倒数排名；nDCG@5 使用单目标文档口径，仅第一次命中贡献折扣增益。

7. **检查重排是否真正执行。** 按当前 LLMReranker 默认参数，使用混合结果前 10 条，每条截取 180 个字符，temperature=0，最多输出 800 tokens，按返回分数重排。记录完整响应、调用耗时、评分覆盖率及异常类型。失败回退或评分不完整不当成成功重排；成功子集需与同一子集的向量和混合结果比较，不能与全量平均值混比。

## 4. 实现与环境边界

当前环境缺少 qdrant-client，依赖安装的自动审批服务故障。因此使用只读 SQLite 快照获取已有向量，由 NumPy 进行精确余弦搜索，仅替换存储访问，检索融合仍运行项目原有实现。已有向量库没有重建、写入或删除。本次结果属于现有索引上的检索算法对比，没有验证 Qdrant 客户端完整调用链，也不能将耗时视为 Qdrant 或线上端到端延迟。

每条查询的向量仅生成一次并缓存，供两种检索共享。已保存逐条排名、指标、语料及代码哈希。`retrieval_elapsed_ms` 包含该查询两种路径及首次缓存写入，仅用于诊断；不能拆成公平的单路径性能对比。当前重排仅有一次失败请求，因此没有有效的重排平均延迟或吞吐率。

## 5. 标签局限与典型案例

该集合每题只有一个指定目标，但知识库中存在多个可回答同一问题的文档，指标衡量的是找回指定目标，不等同于全部相关证据的召回率或最终答案正确率。例如“运费是按什么标准收取的？”标注为 faq-43，混合检索第 1 条是另一个同样讨论运费的 faq-5；未扩充标签前，这仍会算目标未命中。不能为了提升结果，在看过排名后直接改标签再报告同一组提升。

| 查询 | 目标 | 纯向量排名 | 混合排名 |
|---|---|---:|---:|
| 适合学生和行政办公用的笔记本电脑 | product-NB002 | 7 | 3 |
| 搭载 Zenon X5 处理器和 8GB 内存的手机是哪款？ | product-PH001 | 10 | 5 |

此外，这批查询部分与原文措辞接近，且没有无答案问题、用户真实日志或独立留出集。高命中率不能直接外推到线上；本次也没有评测最终回答的忠实度、完整性或幻觉。

## 6. 重排能提升什么

重排只改变候选的顺序，无法找回没有进入候选集的文档。当前默认重排只处理 10 条，因此 Recall@10 在成功返回全部 10 条时必然与混合 Recall@10 一致。混合候选 Top-10 命中率为 98.89%，这是这批数据上默认重排配置的 Recall@5 理论上限；从 98.15% 最多提高到 98.89%（+0.74 个百分点），这不是实测增益。两种检索的 Top-20 都覆盖全部 270 个目标；扩大重排候选到 20 可能提高上限，但属于另一组实验，不能与当前配置混用。

下一步先恢复模型请求并跑完默认重排对照，再决定是否另测完整片段、20 候选或 CrossEncoder。候选覆盖率已接近饱和，重排的收益更可能体现在 Recall@1、MRR 等前排质量上，仍须实际测量。

## 7. 复现与输出

从项目根目录运行（需要 numpy、requests、pydantic，以及可用的本地 BGE-M3 服务）：

```bash
python -m eval.evaluate_retrieval --skip-rerank
python -m eval.analyze_retrieval
```

模型 API 可用后，先在独立目录验证一条，成功后补跑完整重排：

```bash
python -m eval.evaluate_retrieval --limit 1 --output eval/results/2026-09-28/rerank-pilot
python -m eval.evaluate_retrieval
```

重排会使用项目配置的模型服务，对 270 条查询及各自候选片段发起评分调用。无需重新入库；后一次完整命令复用已保存的查询向量。相同配置下可复用成功重排结果，失败请求会重新尝试。

- 评测程序：`eval/evaluate_retrieval.py`。
- 对比分析程序：`eval/analyze_retrieval.py`（本报告聚焦当前已完成的前两组）。
- 全量指标与分类结果：`eval/results/2026-09-28/baseline/metrics.json`。
- 逐条结果、原始分数及排名：`eval/results/2026-09-28/baseline/per_query.json`。
- 方便表格查看的排名：`eval/results/2026-09-28/baseline/query_ranks.csv`。
- 增益、退化与置信区间：`eval/results/2026-09-28/baseline/analysis.json`。
- 语料审计和配置哈希：同目录下 `audit.json`、`provenance.json`。
- 首条重排失败记录：`eval/results/2026-09-28/per_query.json`。
