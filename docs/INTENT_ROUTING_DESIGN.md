# 入口意图路由与固定工作流

设计：2026-09-26；第一版实现：2026-10-10。

状态：入口三路分流、三个单商品固定流程与默认 LLM 延迟创建已实现。使用真实本地数据与模型替身完成离线验证，未调用真实模型；分类准确率和实际成本收益尚未评测。

## 目标与执行路径

在进入 ReAct 前选择合适的路径。第一版优先保证完整保留用户需求，再评估成本和延迟。

| 路径 | 适用请求 | 例子 | 回答方式 |
|---|---|---|---|
| direct | 纯社交、明确无关请求，或缺少必要信息 | “你好”“谢谢”“查库存”但没有可确定的商品 | 程序选定固定话术 |
| workflow | 单个商品的一项简单查询，编号能够可靠确定 | “NB001 有货吗”“NB001 多少钱”“NB001 参数” | 调工具、核验结果、模板回复 |
| agent | 推荐、比较、多目标、条件任务、解释及固定流程未覆盖的业务 | “推荐剪辑电脑”“NB001 有货吗、多少钱” | 原有 ReAct 循环 |

不恢复 Reflection，不增加 Skill、可视化流程引擎或插件注册层。规则和固定流程是程序代码。

## 模块分工

| 文件 | 职责 |
|---|---|
| routing/intent_router.py | 完整请求规则、一次模型分类、候选结果核验与回退 |
| prompts/routing.py | 分类说明和固定话术 |
| workflows/product_queries.py | 库存、价格、通用参数的固定查询、结果核验和格式化 |
| agent/core/types.py | RouteDecision、RunTrace、TurnResult |
| agent/core/runner.py | 请求生命周期、分派、历史与状态收尾、用量统计 |
| agent/core/loop.py | 原有 ReAct 执行，不参与路由 |
| bootstrap.py | 创建并注入 Router、Workflows、Executor、Summarizer |
| llm/client.py | LLMClient 请求适配与 LazyLLMClient 延迟初始化 |

Agent 核心通过注入使用路由和流程，不导入电商规则。直接创建未传 router 的 ConversationRunner 时，仍使用原来的 ReAct 路径。

## 路由顺序

1. 完整匹配空输入、问候、感谢、告别，直接回复。
2. 多个编号、多个查询目标、推荐、比较、条件、售后等复杂请求直接交给 Agent。
3. 识别单商品查询，以及刚刚发出澄清后的编号回复；参数明确则执行固定流程，缺少或存在歧义则澄清。
4. 规则未命中时，最多发起一次分类请求。分类器只识别意图和参数，不调用工具、不生成业务答案。
5. 程序核验候选结构、意图冲突、参数来源与固定流程可用性。非法、无法可靠分类或缺少相应工具时，保留原始请求回退 Agent。

分类器接收当前输入和最近十条 user/assistant 原文；当前输入不重复放入历史，不使用滚动摘要推断商品编号。分类与 Agent 默认共用模型客户端，分类使用低温度、小输出预算并关闭额外思考。

候选 JSON：

```json
{
  "intent": "inventory_lookup",
  "product_id": "NB001",
  "source": "current_input"
}
```

IntentCandidate 使用 Pydantic 严格校验，拒绝额外字段。intent 为固定枚举；source 为 current_input / history / none。参数缺失时 product_id=null、source=none。分类器不能指定任意函数执行。

程序最终生成 RouteDecision：

| 字段 | 含义 |
|---|---|
| kind | direct / workflow / agent |
| intent | 具体意图 |
| params | 固定流程使用的参数 |
| reply | 从模板中选定的直接回复 |
| reason | 分派或回退原因码 |
| source | rule / classifier / fallback |
| parameter_source | 编号来自当前输入、历史或无参数 |

不使用模型自报置信度作为执行依据。结构与来源检查不能证明语义分类绝对正确，仍需要真实请求评测。

## 分流与参数边界

| 请求 | 当前处理 |
|---|---|
| “你好”“谢谢” | 固定回复，零模型调用 |
| “你好，NB001 多少钱” | 保留价格需求，固定查询 |
| “查库存” → “NB001” | 第一轮澄清，第二轮规则接续，无需分类 |
| “它有货吗” | 最近原文只有唯一、未被取消的商品编号时沿用，否则澄清 |
| “好的”“继续”“就它吧” | 保留上下文交给 Agent，不当作通用闲聊 |
| “NB001 有货吗、多少钱” | 多目标交给 Agent，不能只答库存 |
| “如果有货就推荐配件” | 条件任务交给 Agent |
| “NB001 的 CPU 和内存是什么” | 指定规格字段交给 Agent；第一版模板只处理通用参数 |
| “NB001 不要了，查 NB002 库存” | 出现多个编号时保守交给 Agent，保留完整修改要求 |
| “你们太差了，NB001 到底有没有货” | 可由一次分类识别库存查询，不因语气拒绝 |
| 正常投诉、退货、售后 | 有效业务，交给 Agent |
| 无关或没有可处理目标的表达 | 分类确认后固定引导；程序发现业务词或编号冲突时回退 Agent |

快捷路径支持 1～8 个英文字母后跟 3～12 位数字的编号，如 NB001；其他编号格式交给 Agent，不改变原有工具参数契约。

编号必须能从输入或近期原文找到。当前明确编号优先；历史有多个编号、取消过对象或超出可见范围时，不猜测。分类器从历史借用编号还要求本轮有明确指代表达，不能把新的商品名称强行映射为历史编号。编号能追溯不等于商品一定存在，不存在由工具的合法空结果表达。

## 固定流程

固定步骤：核验流程必需参数 → 调用现有 Provider → 解析并检查 JSON → 模板回复。

| 流程 | 必需参数 | 工具 | 结果检查 |
|---|---|---|---|
| inventory_lookup | product_id | check_inventory | 商品身份、名称、非负整数库存、布尔有货状态及两者一致性 |
| price_lookup | product_id | get_product_detail | 商品身份、名称、有限且非负的价格 |
| product_detail | product_id | get_product_detail | 商品身份、名称、实际展示的规格字段类型 |

SingleProductArgs 要求单个编号必填，避免工具的可选参数意外触发全库库存查询。Provider 继续使用原来的 Pydantic 工具参数模型校验；流程不直接访问业务文件。

每次固定流程至多一个工具调用，不使用回答生成模型。正常结果必须是数组；单商品最多一条对象记录，不能随便取第一条。不允许错误商品、多个结果、矛盾库存或非法字段被格式化为成功答案。

| 结果 | 用户侧处理 |
|---|---|
| 库存为零 | 明确显示本地库存记录为零 |
| 合法空数组 | 未查到相关记录，不等同于零库存 |
| 缺少规格 | 省略未提供的字段并说明，不能编造 |
| 工具异常、非法 JSON、异常结果结构 | 明确查询失败、暂时无法确认，并记录错误 |
| 执行前缺少对应工具 | 回退 Agent，保留现有无工具处理 |
| 执行后发生失败 | 本轮结束，不转 Agent 重复查询 |

显示内容明确为本地数据记录，不宣称外部实时价格或库存。工具原始结果保存在 trace；没有新增工具结果压缩。

## 会话、轨迹与用量

ConversationRunner 在路由之前记录用量起点、创建新的 AgentState，并写入当前用户输入一次。路由使用的历史与本轮输入分开传入。

三条路径共用历史、状态和最终结果收尾：每轮用户输入与最终回答各记一次。RunTrace.route 保存决策及路由耗时；固定流程沿用 tool_events 的 intent/result 结构，失败额外记录 error，并将完整工具往返写入本轮 state.messages。

step 只计 ReAct 循环，直接回复和固定流程均为零。completed 仅表示正常返回，包括查询失败的明确回复，不代表任务一定成功。

TurnResult 仍只有 replies 和 usage：

- llm_calls 包含分类、摘要及 ReAct 的应用层 SDK 请求；failed_llm_calls 记录失败次数。
- token 来自服务端 usage；失败时没有取得 usage 的 token 无法统计，不代表实际没有费用。
- latency_ms 是模型请求耗时之和；elapsed_ms 为整轮耗时，包含分类、工具和本地处理。
- 同一个共享客户端的日志增量只统计一次；底层 SDK 内部重试未逐次统计。
- 现有用量归属和延迟客户端按顺序调用设计，尚不支持并发会话的准确归属统计。

默认 LLM 首次 chat() 才读取 .env、创建 SDK 客户端并注册关闭回调；规则覆盖的直接回复和本地单商品查询不依赖模型配置。应用关闭实际创建的 SDK，并阻止关闭后再延迟创建。

## 与会话摘要的关系

只有本轮进入 Agent 路径才尝试压缩历史。直接回复和固定流程不会为了摘要额外请求模型，原文先保留到下一次 ReAct 运行。

因此连续只走快捷路径时，未压缩原文可能超过 20 条。当前不静默删历史，原文归档、token 预算和容量硬上限仍待设计。路由自身只读取最近十条原文。

## 调用预算与验证

| 路径 | 应用层模型请求 | 工具调用 |
|---|---|---|
| 规则直接回复 | 0 | 0 |
| 规则单商品查询 | 0 | 1 |
| 分类后直接回复或澄清 | 1 | 0 |
| 分类后单商品查询 | 1 | 1 |
| 规则直接转 Agent | 原 ReAct 请求，达到阈值时另含摘要 | 由 Agent 决定 |
| 分类后转 Agent | 上述请求再加一次分类 | 由 Agent 决定 |

整体收益取决于请求分布；复杂请求可能多一次分类调用，不能仅凭快捷路径推断总成本一定下降。

```bash
python -m unittest discover -s tests -v
```
